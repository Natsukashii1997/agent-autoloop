# 开发实录与坑

踩过的坑记在这里，Claude 和 Codex 都读。排障、发布、改脚本之前，先搜一遍：`grep -n 关键词 docs/LESSONS.md`；换个项目也成立的坑在全局 `/Users/nat/Documents/ChatGPT/个人/work/agent-kit/LESSONS.md`（G-xx），也搜一遍。

## 怎么写

- 每轮交接时自问「本轮踩到新坑了吗」：有就在下面追加一条，并在 CURRENT.md 的交接里写「本轮新坑：L-xx」；没有就写「无」。
- 一条一个坑，编号只增不改。写现象、根因、正确做法、证据。证据写到能查的程度（提交号、文件与章节、证据目录）；查不到就写「未核实」，不编。
- 结论被推翻时改条目并注明日期，不删。

## 怎么升级

- 同类坑第 2 次出现：把正确做法写进 AGENTS.md 或 docs/OPERATIONS.md（一句话硬约束进 AGENTS.md，操作细节进 OPERATIONS.md），条目的「升级」改成写到了哪里。
- 能用机器判定的：写成测试或脚本（如 `scripts/check-rules.mjs`），条目注明。
- 换个项目也成立的（不依赖本项目的业务、页面、发布脚本）：提议提升到全局坑 `/Users/nat/Documents/ChatGPT/个人/work/agent-kit/LESSONS.md`，写成 G-xx；原条目保留，末尾加一行「提升：已提升为全局 G-xx（日期）」。只出提案，用户批准才写。
- 条目超过约 30 条时整理一次：已升级、且之后没再犯的，归档到 `docs/history/`。
- 「升级」一行每条都要有，开头写层级词〔结构〕〔机检〕〔体检〕〔文字〕〔提醒〕之一，再写状态（未升级 / 不升级 / 部分升级 / 已升级 / 关闭）、日期、编号和去处；还没升级的写「〔提醒〕未升级。」。坑本身已被代码消除、不再需要升级的写「〔层级〕关闭（日期，依据）：证据」，层级写现在靠什么守住（回归测试没接进必经检查的写〔提醒〕），原来的记录保留。层级的含义和怎么选，以全局 LESSONS「怎么升级」为准。`scripts/check-rules.mjs` 会查。

## L-01 文字截断前后修了 5 次，几处各切各的，按编码单元切会切断字符（2026-11-04 起）

- 现象：卡片回答和通道回报的长度上限只写在 schema 里，内核没执行（#40）；之后事件来源插件、交付通知、通道失败原因又各自因为按 `slice(0, 数字)` 切字被修了一遍，切断 emoji 或汉字组合字符，或切掉了要留的结尾（#259 #280 #284 #292）。
- 根因：截断没有统一入口，每处自己 `slice`；JS 字符串按 UTF-16 编码单元计数，切点可能落在一个字符中间；上限值散在 schema 和代码两处。
- 正确做法：给人看的文字截断一律用 `worker/contract.ts` 的 `fit()`；新加上限时，内核和 schema 读同一个常量；修一处截断先 `git grep -nE "\.slice\(0, ?[0-9]+\)"` 搜同类。
- 证据：`7793cd2`（#40）、`45aecbf`（#259）、`d26c7f2`（#280）、`55e5827`（#284）、`d3a44ca`（#292）；跨项目复盘 2026-10-18～11-18「同一错误反复修」一节。
- 升级：〔提醒〕未升级。可升到〔机检〕：在 `scripts/check-rules.mjs` 里对源码目录的字符串 `.slice(0, 数字)` 报错（复盘建议，未批）。

## L-04 命令参数解析出过 5 次错，合成一张表之后没再出现（2026-11-05）

- 现象：多个命令各自解析参数，不认识的参数被悄悄忽略、`--help` 行为不一致，前后修了 5 次。
- 根因：每个命令各写一套参数解析。

- 升级：〔结构〕已升级（2026-11-05，#108）：`cli/main.ts` 的 `TAKES` 表和 `refuseUnknownFlags`，不在表里的参数写不进去。

## L-05 进程死活判断前后修了 4 次，「确认不了」被当成「已结束」（2026-11-06 起）

- 现象：接单程序确认不了进程组已结束时交了 cancelled（#146），自己停的轮次看不到进程组时又交了 failed（#152），Windows 上查进程卡住中台（#179）。
- 根因：探活只有「活着 / 没了」两种结果，「不知道」被并进其中一种；停止原因没有穷尽判断。
- 正确做法：探活结果分「活着 / 没了 / 不知道」三态，「不知道」单独处理；停止原因用联合类型加穷尽判断，加新原因时编译器会指出漏掉的分支。
- 证据：`a93b194`（#146）、`e61ccfd`（#152）、`b8df97b`（#179）；第 4 次未核实是哪个提交；跨项目复盘「改造建议」一节。
- 升级：〔提醒〕未升级。可升到〔结构〕：三态探活加穷尽判断（复盘建议，未批）。

## L-06 等真实事件的测试只给 2 秒，机器忙时偶发失败，会拦住推送（2026-11-20）

- 现象：`npm run test:quick` 全量并发跑时 `feishu: U+2028 and U+2029 in a handling note don't lose the click` 失败（用时 2003ms，答案为空）；单独跑 3 次都过（617～1438ms）。同日铺骨架时全量再跑又失败（2005ms），两次都卡在 2 秒上限。

- 正确做法：等真实事件的测试写成「事件一到就结束，否则等到足够长的上限」，上限按机器最忙时估，不按单跑的耗时估；推送前钩子因为计时用例失败时，先单独重跑那一条确认，不用 `--no-verify` 绕过。
- 证据：dt@`f293b9b` 上本机快速测试 808 条、1 条失败（2026-11-20 两次）；上限改为 20 秒后全量 787 过、0 失败，这一条 261ms（`~/Library/Application Support/agent-autoloop/evidence/2026-11-20-starter/test-quick-2.log`）。同类：`git grep "setTimeout(resolve, " tests` 里「等事件或到上限」的写法只有这一处。
- 升级：〔提醒〕部分升级（2026-11-20）：这一条的上限已改为 20 秒；以后新写的计时用例没有机器检查。

## L-07 安装测试在终端里都过，到推送前钩子里 3 条失败：git 把自己的 libexec 放进了 PATH（2026-11-20）

- 现象：第一次带钩子推送，`tests/releases.test.ts` 的 3 条安装测试失败，报 `git-upload-pack: command not found`；同一提交在终端里跑 `npm run test:quick` 全过。
- 根因：git 运行钩子时把 `$(git --exec-path)`（本机是 `/Library/Developer/CommandLineTools/usr/libexec/git-core`）放在 PATH 最前面，并设 `GIT_EXEC_PATH`。测试用 `command -v git` 找 git，在钩子里找到的是 libexec 里那份；测试换了 PATH 再跑它，它按自己所在位置推算 libexec，找不到 `git-upload-pack`。和全局 G-46 同属「钩子里的环境和终端不一样」。
- 正确做法：钩子在跑检查前，除了 `unset $(git rev-parse --local-env-vars)`，还要把 exec-path 从 PATH 开头去掉、`unset GIT_EXEC_PATH`；钩子改动的验收必须真推一次，不能只在终端里跑测试命令（G-47）。
- 证据：`~/Library/Application Support/agent-autoloop/evidence/2026-11-20-starter/push.log`（`ℹ fail 3`）；复现用例 `tests/hooks.test.mjs`「测试命令找到的 git 和终端里一样」，改前红、改后绿。
- 升级：〔机检〕已升级（2026-11-20，本 PR）：`scripts/hooks/pre-push` 去掉 exec-path 和 `GIT_EXEC_PATH`，`tests/hooks.test.mjs` 的复现用例随推送前钩子必跑。起步骨架（my-skills project-starter）和其他 8 个仓库的同一钩子没改，提议同步、并提升为全局坑，待批。
